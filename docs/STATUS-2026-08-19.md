## What changed in the repo, and why

### 1. UTF-8 client encoding — `scripts/setup-home-postgres.ps1` (commit `3e53a95`)

`008_link_past_student_audiograms.sql` contains Cyrillic (`NOT ILIKE '%тест%'`)
and is stored as UTF-8. psql takes its client encoding from the Windows console
codepage, which on the home PC is **WIN1252** — no Cyrillic in it, so psql
refused the file:

```
ERROR: character with byte sequence 0x81 in encoding "WIN1252" has no equivalent in encoding "UTF8"
```

Fix — one line, applied to every psql call the script makes:

```powershell
$env:PGCLIENTENCODING = 'UTF8'
```

This never appeared at work because that machine runs a Cyrillic codepage.
Any future machine could hit it, so the fix belongs in the script, not in the
environment.

### 2. Migration 004 made re-runnable — `database/migrations/004_schedule.sql` (commit `49c5b30`)

`004` created the `schedule_conflicts` view with `CREATE OR REPLACE`, and `007`
later redefines the same view with **more columns**. On a fresh database the
order works. On any re-run, `004` meets `007`'s wider view and PostgreSQL
refuses, because `CREATE OR REPLACE VIEW` cannot drop columns:

```
ERROR: cannot drop columns from view
```

Fix:

```sql
DROP VIEW IF EXISTS schedule_conflicts;
CREATE VIEW schedule_conflicts AS ...
```

`007` still recreates the view afterwards, so the end state is unchanged.

### 3. Migrations ledger — `scripts/setup-home-postgres.ps1` (commit `49c5b30`)

The underlying cause of #2: the script applied **every** `.sql` file on **every**
run, which made correctness depend on all nine migrations being individually
re-runnable. That holds today only because every one of them happens to use
`IF NOT EXISTS`, `DROP CONSTRAINT IF EXISTS`, or `ON CONFLICT` — an invariant
nobody is enforcing. The first plain `ALTER TABLE ... ADD COLUMN` in migration
010 would break setup on every machine that already had it.

The script now keeps a ledger:

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
    filename   text PRIMARY KEY,
    applied_at timestamptz NOT NULL DEFAULT now()
);
```

It reads the ledger, applies only the files not listed, and writes each file's
ledger row **inside the same transaction as the migration itself** (`psql -1`),
so a file either fully applies and is recorded, or neither. Files already
applied print `Already applied: …` and are skipped.

This is what Flyway, Alembic and Drizzle do underneath. It also means the two
machines can no longer silently disagree about which migrations they have run.

### 2. Seed the ledger — do **not** just rerun the setup script

The work database already has all nine migrations applied, but it has no
`schema_migrations` table, so the script would consider all nine unapplied and
re-run them. They are idempotent, so this is *survivable* — but there is no
reason to replay nine migrations across a database holding real student data.
Record them as applied instead:

```powershell
$env:PGPASSWORD='therapy_local'
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U therapy -h localhost -d therapy_dev -c "CREATE TABLE IF NOT EXISTS schema_migrations (filename text PRIMARY KEY, applied_at timestamptz NOT NULL DEFAULT now()); INSERT INTO schema_migrations (filename) SELECT unnest(ARRAY['001_app_state.sql','002_core_tables.sql','003_sdnevnik_id_bigint.sql','004_schedule.sql','005_attendance_plans.sql','006_clinical_records.sql','007_school_years.sql','008_link_past_student_audiograms.sql','009_diary_schedule_links.sql']) ON CONFLICT DO NOTHING;"
```

```powershell
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U therapy -h localhost -d therapy_dev -c "SELECT filename FROM schema_migrations ORDER BY filename;"
```

From then on both machines behave identically: migration `010` will be the only

### Import findings, all benign

- **`ids generated (legacy): 82`** — the May backup predates `studentMeta.studentId`,
  so all 82 ids were derived by `stableStudentIdForName()`. That function
  mirrors the app's own generator byte for byte, so the ids are identical to
  the ones the work PC produces for the same names. Nothing will diverge.
- **16 of 16 S-Dnevnik students linked via bare name.** Rasporedi stores names
  grade-prefixed (`"IV-а - Мирем Османова"`), S-Dnevnik stores them plain with
  the grade in its own field. The importer strips the prefix and matches — and
  in all 16 cases the S-Dnevnik grade agrees with the stripped prefix, which is
  the second signal that makes the match trustworthy.
- **6 double-booked students** — real scheduling conflicts in the May data,
  imported as-is rather than dropped. They appear in the `schedule_conflicts`
  view whenever you want to resolve them.
- **Diary data for 3 student ids skipped** (`1759559487992`, `1759559525361`,
  `1759559570888`) — millisecond timestamps from early October 2025. Students
  added then and later removed from the roster; their diary rows have nothing
  to attach to. Only worth chasing if those three records are still wanted.
- **No `problems` section was printed**, i.e. zero problems.
